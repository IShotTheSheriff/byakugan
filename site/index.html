byakugan builds the graph of code your Next.js app uses, down to single exports. CI asks it one question per app: can this pull request change what the app does? When the answer is no, skip the end-to-end tests and the build.

The eye that sees through.

Where the name comes from, and why it fits.

The white eye

Byakugan (白眼, "white eye") is the eye technique of the Hyūga clan in the manga and anime Naruto. Its user sees in almost every direction at once, sees through walls, and sees the chakra network, the paths along which energy flows through a body. A Hyūga fighter does not guess where to strike. They look at the network and hit the one point that matters.

The same idea, for code

An app is a network too. Imports flow from a page through barrel files, across package boundaries and into node_modules. byakugan looks through those walls and traces every path from an entry file to the declarations it uses. A change either sits on a path or it does not. That is the whole verdict.

byakugan is an open source tool and is not affiliated with Naruto or its publishers. The npm package is byakugan-cli.

CI was sized for people.

A software factory of coding agents opens pull requests all day. Each one pays for the whole pipeline.

More pull requests

A team with agents merges many small changes: a copy fix, one refactored helper, a dependency bump. Each push runs installs, builds and a browser suite that takes longer than writing the change did.

Coarse answers

Turborepo, Nx and path filters decide per package or per file. Someone edits Modal in @acme/ui, and every app that depends on @acme/ui rebuilds, whether it renders Modal or not. A lodash release touches filter, and everything rebuilds again.

Slow loops

An agent waits on CI before it can merge or try again. A 25-minute suite on a change that could not reach the app is 25 minutes of queue for every pull request behind it, and runner minutes on the bill.

Follow the imports.

byakugan walks from the app's entry files, symbol by symbol, and hashes exactly what it reaches.

  1. Entries

    For Next.js, every App Router file (page, layout, route, loading, error, metadata routes), everything under pages/, middleware or proxy, instrumentation and next.config.*. Every export of an entry counts as used.

  2. Fragments

    The oxc parser splits each reached module into fragments: top-level declarations, import bindings, export specifiers, export * lines and the module's side effects. byakugan records which top-level names each declaration refers to.

  3. The walk

    A used export leads to its declaration. The declaration leads to the names it refers to. An import leads to the export it resolves to, through tsconfig paths, package exports, barrels, import(), next/dynamic and workspace symlinks. An import type is followed through types only, so the target module does not run.

  4. Modules that run

    Importing a module runs it, so its top-level statements count even when no export is used. Packages with "sideEffects": false are skipped unless a binding is used, as bundlers do.

  5. The hash

    The fingerprint is SHA-256 over the sorted (key, hash) pairs of every live fragment. A fragment's hash comes from its syntax tree, so comments, whitespace, quote style and a Prettier run with other settings leave no trace.

Beyond imports

What a Next.js app depends on without importing it

  • import(`../messages/${locale}.json`) counts every file the pattern matches.
  • localFont({ src: './fonts/brand.woff2' }) counts the font file.
  • join(process.cwd(), 'content', slug) counts every file under content/.
  • 'use server' counts every export, since each can be an endpoint.
  • Tailwind: byakugan runs the project's own Tailwind and hashes the CSS it generates. A workspace package that Tailwind scans through node_modules is read once and compared with its base version.
  • NEXT_PUBLIC_* values that live code reads are part of the fingerprint.
Besides code

What else is in the fingerprint

  • package.json, the tsconfig chain, .env* and public/**.
  • The installed version of tools that read the app without being imported: next, react, typescript, tailwindcss, postcss.
  • The used files of each npm package. import { partition } from 'lodash' is 123 of lodash's roughly 1,050 files.
  • Keys are relative paths and npm:<package>/<file>, so fingerprints match across machines and pnpm store layouts.

Speed

On a Next.js app with 58 npm packages a run takes 0.7 s. Eight apps over one 6,000-module shared package take about 8 s with --workspace, because a shared file is parsed once.

Two promises, your pick.

A verdict promises the same behavior, or the same build output too.

behavior

The app runs the same

The default. byakugan counts the code the app can run. Use it to skip end-to-end tests, unit tests and visual tests.

--strict

The build is the same

Also counts code the bundler ships but nothing runs. Next.js ships a 'use client' module whole when a server component imports it. Use it to reuse a build artifact or skip a deploy.

Start with the doctor.

Three commands take you from install to a first verdict.

npm install --save-dev byakugan-cli

# find the apps and what needs fixing
npx --no-install byakugan doctor --workspace

# which apps does this branch change?
npx --no-install byakugan affected --workspace --base origin/main

With one app, leave out --workspace and run the commands in the app directory. The command needs Node.js 22.12 or newer. npx --no-install matters: an unrelated npm package is named byakugan.

Tell it what it cannot see.

A byakugan.json next to the app's package.json is optional. It names what byakugan cannot detect, and it makes a directory an app.

{
  "entry": ["scripts/seed.ts"],
  "inputs": ["messages/*.json"],
  "virtual": ["~icons/**"],
  "env": ["API_*"],
  "conditions": ["source"]
}

With --workspace, every package that has a byakugan.json gets a verdict of its own, even a library or a test package with no framework. byakugan rejects a file that is not valid JSON or has a field of the wrong type.

FieldWhat it does
entryExtra entry files (globs). Every export of an entry counts as used.
inputsFiles hashed whole, for files a tool reads without an import, such as messages/*.json.
packagesPackages counted by installed version, for tools that read the code without being imported.
virtualSpecifiers a bundler plugin provides, such as ~icons/**. Without it, an import that does not resolve makes every run "affected".
generatedGit-ignored files the build generates, such as a Prisma client. List the generator's inputs in inputs.
envEnvironment variables whose values count when live code reads them, added to NEXT_PUBLIC_* and VITE_*.
conditionsExport conditions tried first. Use ["source"] when workspace packages point exports at dist.
modularizeImportsThe Next.js option of the same name, merged over the built-in rule for lodash.

jsxImportSourceDefaults to the tsconfig option, then react.

Recipes for your pipeline.

GitHub Actions steps you can paste. Each one runs after the install step, with fetch-depth: 0 on checkout.

Recipe 1

Skip the end-to-end tests of one app

affected writes affected=true|false to $GITHUB_OUTPUT. A failed step fails the job, so an error never skips anything.

- uses: actions/checkout@v7
  with:
    fetch-depth: 0   # affected needs the merge base
- run: npm ci
- id: web
  env:
    BASE_REF: ${{ github.base_ref }}
  run: npx --no-install byakugan affected -C apps/web --base "origin/$BASE_REF"
- if: steps.web.outputs.affected != 'false'
  run: npm run e2e --workspace web
Recipe 2

A monorepo: one run, one job per affected app

With --workspace, apps= is a JSON list of the affected app directories. Fan out with a matrix.

jobs:
  affected:
    runs-on: ubuntu-latest
    outputs:
      apps: ${{ steps.byakugan.outputs.apps }}
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }
      - run: npm ci
      - id: byakugan
        env:
          BASE_REF: ${{ github.base_ref }}
        run: npx --no-install byakugan affected --workspace --base "origin/$BASE_REF"
  build:
    needs: affected
    if: needs.affected.outputs.apps != '[]'
    strategy:
      matrix:
        app: ${{ fromJSON(needs.affected.outputs.apps) }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - run: npm ci
      - env: { APP: "${{ matrix.app }}" }
        run: npm run build --prefix "$APP"
Recipe 3

Playwright in a monorepo

End-to-end specs drive a browser and do not import app code. Run the suite when a change reaches an app it talks to, or the test package itself. This byakugan.json in the test package makes an edited spec count:

{ "framework": "none", "entry": ["tests/**/*.spec.ts", "playwright.config.ts"] }
e2e:
  needs: affected
  if: >-
    contains(fromJSON(needs.affected.outputs.apps), 'apps/web') ||
    contains(fromJSON(needs.affected.outputs.apps), 'apps/api') ||
    contains(fromJSON(needs.affected.outputs.apps), 'e2e')
Recipe 4

Reuse a Next.js build when nothing it uses changed

The fingerprint is the cache key. It hashes the installed files the app uses, so a dependency bump that touches other files keeps the key. --strict makes the key cover everything the build emits.

- id: web
  run: npx --no-install byakugan hash -C apps/web --strict
- id: cache
  uses: actions/cache@v6
  with:
    path: apps/web/.next
    key: web-next-${{ steps.web.outputs.fingerprint }}
- if: steps.cache.outputs.cache-hit != 'true'
  run: npm run build --workspace web
Recipe 5

Only the tests and stories a change reaches

--each gives one verdict per matching file. A barrel still splits by export: an edit to Card reaches the test that imports Card, and not the one that imports Button from the same file. Runner configs and .storybook/preview reach every file.

# unit and component tests
npx --no-install byakugan affected --base origin/main --each 'src/**/*.test.{ts,tsx}' > tests.txt
[ -s tests.txt ] && xargs npx vitest run < tests.txt

# Storybook stories, for visual tests
npx --no-install byakugan affected -C packages/ui --base origin/main --each 'src/**/*.stories.tsx'
Recipe 6

Turborepo and Nx

Both decide per package or per project. Let byakugan choose the apps, and let the task runner run and cache the tasks.

apps=$(npx --no-install byakugan affected --workspace --base origin/main --json \
  | jq -r '.affected[] | "--filter=./" + .')
[ -n "$apps" ] && npx turbo run build e2e $apps
Recipe 7

Check byakugan against real builds first

Before you skip anything, run in shadow mode. Build every pull request, and when byakugan says unaffected, build the merge base too and compare. A failing compare names the files that differ.

- id: web
  run: npx --no-install byakugan affected -C apps/web --strict --base "origin/$BASE_REF"
- run: npm run build --workspace web
- if: steps.web.outputs.affected == 'false'
  run: |
    git worktree add ../base "$(git merge-base "origin/$BASE_REF" HEAD)"
    (cd ../base && npm ci && npm run build --workspace web)
    npx --no-install byakugan compare ../base/apps/web/.next apps/web/.next

Where it can be wrong.

A wrong "affected" costs one extra run. A wrong "unaffected" ships something untested. byakugan picks the first kind where it can.

Costs extra runs

  • CommonJS files are hashed whole.
  • There is no type checker. A declaration reached through import type counts whole.
  • Git mode sees dependency updates per package. A saved manifest sees them per file.
  • An import byakugan cannot resolve counts as affected on every run.

Can miss a change

  • Data fetched at build time: a CMS, a database.
  • File paths and imports built from variables. doctor warns about them.
  • Environment variables that config files read, unless "env" names them.
  • Aliases that exist only in bundler config. Put them in tsconfig paths.

byakugan has no sandbox. Trust comes from checking it against real builds with byakugan compare. Read the full list of limits

Frequently asked questions

How is this different from Turborepo or Nx affected?
They work per package or per project: a change in a package affects everything that depends on it. byakugan works per export and per file inside npm packages. It does not run or cache tasks, so the two fit together. byakugan picks the apps, the task runner runs them.
How does it relate to Knip?
It is Knip's approach turned around. Knip walks from entry files through every import and reports what nothing uses. byakugan does the same walk and keeps the rest, the code the app uses, so it can hash it. Both run on the oxc parser and resolver.
Does it work with webpack and Turbopack?
byakugan does not run the bundler. It resolves imports through tsconfig paths and package exports, as both bundlers do. Build comparison was checked against Turbopack builds on Next.js 16. Webpack builds are untested, so run shadow mode before you reuse webpack output.
What about dependency updates?
The fingerprint hashes the installed files the app uses, so a lodash release that only changes filter.js keeps the key when the app uses partition. With --base, byakugan reads the lockfile and counts a bump per package. With --base-manifest, it compares per file.
Does it work with Storybook in a host package?
Yes. Storybook built from a host package compiles every package's stylesheets with the host's PostCSS and Tailwind configs, and its webpack reads the PostCSS config nearest each stylesheet. Set "tailwindDir" to the host and "postcssFromStylesheet": true in byakugan.json to compile them the same way. A graph for a typecheck or unit tests never reads the generated CSS, so "tailwind": false skips Tailwind there.
Which frameworks does it know?
Next.js gets the most attention: App Router, Pages Router, Tailwind, shadcn, server actions. Vite, React Router, Hono and plain TypeScript packages work too. Any package can name its entries in byakugan.json.
Is it safe to run on pull requests from forks?
byakugan reads nothing outside the repository and needs only contents: read. It does run the project's Tailwind, which loads config files from the repository, so run it where you would run the build.
What does it cost?
Nothing. byakugan is MIT licensed and runs in your own CI. It sends no data anywhere.
